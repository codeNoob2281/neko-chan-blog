脚本按 SQLite 写，MySQL 8 不认，直接 1064 语法错误；迁移启动时执行，一挂服务就起不来。

## 幂等从方言挪到 Java 侧

原来把存在性判断外包给了数据库语法——SQLite 的 `IF NOT EXISTS` 能重复执行，MySQL 不认。提交里的选择是**把判断收回应用层**：建表继续用两端都支持的 `CREATE TABLE IF NOT EXISTS`，建索引和加列先查元数据：SQLite 查 `sqlite_master`/`PRAGMA`，MySQL 查 `information_schema`。注释原话：「幂等靠 Java 侧判断，不靠方言语法」。可推广：跨数据库的幂等要用最大公约数实现，JDBC 元数据查询就是，方言快捷语法只是单点优惠。

## DDL 隐式提交：迁移没有事务可回滚

MySQL 的 DDL 隐式提交：迁移执行到一半失败，前面的语句已落库，回滚不了。所以设计目标不是「可回滚」，只能是「可重放」——版本号记在 `ps_schema_history`，重启接上重跑。存在性判断也必须前移：不可回滚时重复执行还不能炸，幂等就从锦上添花变成续命前提。

## utf8 不是 utf8mb4：字符集三层坑

JDBC 连接串里的 `characterEncoding=utf8`，在 MySQL 服务端实际落到 `utf8mb3`，最多 3 字节，emoji 插不进去。直接写 `utf8mb4` 更糟：Connector/J 会抛 `Unsupported character encoding`。正解是写 Java 字符集名 `UTF-8`，驱动映射到服务端 `utf8mb4`；建表钉死 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`。连接串、驱动、服务端三层各叫一个名字，不踩一次记不住。

## 漏到线上的不是方言，是没测的路径

提交里有句自白：

> MySQL 路径以前没任何覆盖，才让 `CREATE INDEX IF NOT EXISTS` 一路漏到线上。

真正的防线是测试：`MigrationDialectTest` 5 个用例、不起数据库，静态审查两种方言的迁移 SQL；`StorageIntegrationTest` 加 `migrationRecoversFromPartiallyAppliedSchema`，专验「迁移执行到一半挂掉、重启后续跑」。

## 事后回看

跨数据库项目里，迁移测试要按「数据库类型 × 迁移版本」做矩阵，只测 happy path 等于没测。开放问题：上 Flyway/Liquibase，这句方言问题还会发生吗？会，只是换种死法——它们管「执行到第几版」，不管「这话在目标数据库上合不合法」。方言检查这层，终究得自己补。[待补充：方言问题首次暴露于什么环境、存在多久，提交里没写。]
