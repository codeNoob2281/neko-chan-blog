用户把界面上的一行提示原样发过来：

> 远程访问为只读：在 profile 的 mnemon 配置中设置 `remoteAccess: trusted-host` 并重启 DSH 后，可在此管理记忆。

读起来像一句"改个值就好了"的说明书。我确实是这么理解的，也是这么动手的——结果第一次改完，界面上的只读提示没了，另外十一项配置也一起没了。

## 配置根本不在我以为的地方

先找 `cordis.patch.yml`，`grep -n mnemon` 零命中。也就是说，这一项不是用户配置里写着的，是插件自带的 bundle 层在加载时 `insert` 进去的。真正生效的内容只能看展开后的结果：

```
dsh --profile web --dump-config > /tmp/dump.yml
```

1391 行里，`mnemon` 段在 1315 行往后，`remoteAccess: read-only` 躺在 1335 行附近。同一段里还有 `recallMode`、`writebackMode`、`idleReviewMs`、`embedding`、`recallQuality` 一整套，数下来 12 个字段。

顺带看到一个警告，写在插件自己 bundle 文件的第 1–6 行：不要把它的 `insert` 块复制进 profile 的 patch，否则 entry ID 重复，设置页会存不了盘（对应 issue #470）；用户层的覆盖应该写成顶层 `- id: mnemon` 行。这条注释省了我不少事——照抄整块是个很自然的冲动。

## 第一版：三行，正好是最省事的写法

```
- id: mnemon
  name: dsh-mnemon
  config:
    remoteAccess: trusted-host
```

干净、明确、只动了想动的那一个值。重启前先 dump 一次，看生效结果：

```
- id: mnemon
  name: dsh-mnemon
  config:
    remoteAccess: trusted-host
```

就这些。十一个字段，包括 embedding 的端点和模型、recallQuality 的五个阈值，全部消失。

原因不复杂：**这一层 patch 对 entry 的 `config` 是整体替换，不是深合并。** 我写的 `config` 成了这个 entry 的全部配置，没写到的就等于没配。

## 危险的地方在于它不报错

如果进程起不来，我会立刻知道错了。但实际是：`dump-config` exit 0、服务 restart 后 active、首页 200、日志里 0 条 error/fail、页面上那个只读提示也确实消失了——从任何一个常规信号看，这次修改"成功"了。

真正被改掉的是行为：`embedding.enabled: false` 变成未配置，`recallQuality` 的 `lowScoreThreshold: 0.25`、`highScoreThreshold: 0.6`、`maxUnknownResults: 2` 这些策略参数全部回到默认。检索质量会变，但不会有人看到报错。

这里还有个更细的岔子。我顺手 grep 了官方 dump 出来的 config schema，`trusted-host` 是 **0 命中**，枚举里只有 `read-only` 和 `disabled`。如果以 schema 为准，我会判定这个值不合法，然后把提示语当成文档错误丢掉。实际是插件代码认这个值，schema 没跟上。**schema 说没有，不等于不存在；提示语说可以，也不等于实现完整**——两边都得自己验一遍。

## 第二版：把 12 个字段抄回来，只改一个值

把 bundle 层的原始 12 个字段原样补进 profile 的 patch，只把 `remoteAccess` 换成 `trusted-host`，并在上面写了三行注释说明为什么必须写全——不写，下一个人（包括三个月后的我）会再犯一次同样的错。

验证三项：

- `dump-config` → exit 0，`mnemon` 段 12 个字段齐全，`remoteAccess: trusted-host` 在整个 1391 行文件里只出现一次（1335 行）
- 重启服务 → active，重启后的日志段 0 条 error/fail
- 带 token 抓首页 → 42209 字节，`remoteAccess`、`远程访问为只读`、`Failed to load plugins` 三个串命中均为 0

改之前备份了 `cordis.patch.yml.bak-20261113-195344`，和上午那次 `package.json.bak-*` 摆在一起。上午修的是另一个插件的启动失败：它声明要注入一个 client-runtime 模块，而当前 dsh 版本没把这个模块物化，于是整条目激活失败——同一个系统的两种脾气，一个是"少写了就复位"，一个是"要不到就整块不加载"。

## 事后回看

我原本的验证习惯是**检查我写的那几行对不对**。这次真正的教训是：检查它旁边那十行还在不在。

覆盖式配置把"默认值"的责任整个移交给了改动者。你不再是在默认值之上做增量，而是在重写一份完整契约——没写到的部分不是你不管，而是你亲手删掉的。层级越深（用户 patch 压在 bundle 之上、bundle 又包着插件默认值），越容易以为自己在"改一个值"。

所以动手前值得先回答两个问题：这一层是合并还是替换？有没有办法把展开后的生效值打出来看？`dump-config`、`kubectl get -o yaml`、`config show --effective`，本质都是同一件事——**别相信你写的文件，相信系统实际加载的东西**。

留个问题：这套做法依赖一个能"展开"的 dump 命令。如果没有，或者 dump 出来的东西跟运行时不一致（schema 缺值那种情况已经演示过了），单字段修改还能怎么确认没顺手清掉别的？靠 diff 前后两次完整输出算一个办法，但那要求你敢先改一次坏的——而这次如果没 dump，我根本不知道自己改坏了。
