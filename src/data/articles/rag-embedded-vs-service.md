一句话定位：**Ru41 是「嵌入式 RAG」的极简实现，solon-ai-example 是「服务化 RAG」的分层实现**。下面按链路拆开比。

## Ru41：一个 SQLite 文件跑完整个 RAG

Ru41 的链路是：Obsidian vault 的 markdown → 切块 → 本地向量化 → 存进 `knowledge.db` → 每条用户消息自动检索注入。全程没有外部服务依赖。

**切块**：剥掉 YAML frontmatter 后按标题层级切，目标 600 字符、硬上限 800、相邻块重叠 80 字符，过短的尾块合并回前一块。块内保留标题路径作为语义上下文，而且送去 embedding 的文本是 `path｜heading\ntext`——**路径和标题当强语义信号一起进向量**。

**存储**：一张 `chunks` 表，f32 向量直接 `to_le_bytes` 拍进 BLOB；建库时把向量维度和模型名写进 meta 表，启动时校验，维度对不上直接报错让你重建索引——防止换模型后静默返回垃圾结果。WAL + 5 秒忙等，解决 obsidian 容器写、worker 容器读的跨容器并发。

**embedding**：fastembed（ONNX Runtime）本地跑 bge-small-zh-v1.5，512 维，模型首次使用自动下载。笔记不出服务器。

**检索**：混合检索是本次更新的重点。向量路全表扫余弦（万块级毫秒级，不做候选剪枝，召回不损）；词面路用 FTS5 虚表 `tokenize='trigram'` 跑 BM25，取前 20。两路结果做 RRF 融合：`score = Σ 1/(60 + rank)`，**不加权**。还有一个很细的处理：FTS 精确命中的文档，对外展示的相关度抬到 0.62 的下限——注释里写得很清楚：书名、课程名、错误码这类精确词是 dense 检索的天然盲区，**词面匹配本身就是证据，不是噪声**。

**注入**：这是 Ru41 和传统 RAG 服务最不一样的地方。它不是「用户主动搜」，而是 worker 里**每条用户消息进 agent 前自动检索**，命中达阈值（余弦 ≥0.45，top3）就渲染成「知识库自动检索结果」块前置到 prompt。配套两个门控：查询长度必须落在 6～1200 字符之间——太短（「你好」）embedding 必中噪声，太长视为机器生成的批量任务直接跳过。检索失败降级为无注入，不阻断任务。

还有一条安全细节：检索块来自 vault 原文，**注入前要过同一条脱敏链路**（Sanitizer），映射并入回填表——不然库里的密码、密钥会经注入直达 LLM，绕过入口脱敏。这个坑踩得很扎实。

## solon-ai-example：父子分段 + 三策略检索

rag-example 的数据模型是三层的：

```
kb_document（原始全文留底，可一键重建索引）
  └─ 父块 kb_chunk（1000 token，存 MySQL）← 检索命中后进 LLM 上下文
       └─ 子块（200 token，存 Milvus）   ← 只用来向量化检索
```

**切分**：markdown 先按标题章节切（上下文继承算法，章节带 `title_path` 元数据），再逐章节用 jtokkit（cl100k_base）按 token 切父子两级——跨章节不合并正文。子块粒度小、召回准；父块粒度大、上下文全。这就是经典的 **small-to-big** 手法。

**embedding 走远程 API**（默认 Ollama bge-m3，1024 维），外面包了一层 `RetryableEmbeddingModel`：超时、瞬断、429 限流按指数退避自动重试，入库和检索两条路共用。

**检索策略模式**：`RagRetrievalStrategy` 接口 + Resolver 按配置从容器里选 Bean，三种策略可热切：

- `parent-child`（默认）：Milvus 检索子块 → 按 `parent_id` 映射回 MySQL 父块 → 父块内容进上下文
- `mysql-fulltext`：MySQL FULLTEXT + **ngram** 中文分词，纯关键词，不依赖 Milvus
- `hybrid-rrf`：两路各取 limit×3 候选，**加权 RRF**：`0.6×Σ1/(60+rank) + 0.4×Σ1/(60+rank)`；任一来源故障自动降级另一路

**工程配套**是这个项目最像「生产代码」的部分：入库线程池（任务粒度=单个文档、CallerRunsPolicy 天然背压）、Milvus 懒连接（启动不要求在线）、INGESTING/INGESTED/FAILED 状态机、依据 `kb_document.content` 一键重建索引。注释里也诚实地标注了取舍：MySQL↔Milvus 双写没有跨库原子性，失败文档保留 FAILED 状态。

**注入侧**走 REST 接口（`/rag/ask` 同步、`/rag/chat/stream` 流式），检索结果填进 SnEL 模板，system prompt 强约束「只依据知识库回答，找不到就如实说」。

## 对照表

| 维度 | Ru41 | solon-ai-example |
|---|---|---|
| 部署形态 | 单二进制，零外部依赖 | MySQL + Milvus + 远程 embedding |
| embedding | 本地 ONNX bge-small-zh（512 维） | 远程 API bge-m3（1024 维）+ 重试 |
| 切分 | 标题切 + 字符 600/800 + 重叠 80 | 章节切 + 父子两级 token 切分 |
| 词面检索 | SQLite FTS5 trigram | MySQL FULLTEXT ngram |
| 融合 | RRF k=60，无权重 | RRF k=60，加权 0.6/0.4 |
| 阈值 | 余弦 ≥0.45，FTS 命中抬到 0.62 | 相似度阈值 0.4 透传两路 |
| 检索时机 | 每条消息自动注入 | 用户显式调 API |
| 查询门控 | 长度 6~1200 字符 | 无（显式调用不需要） |
| 结果脱敏 | 有（Sanitizer 链路） | 无 |
| 一致性防护 | meta 记 dim/model，不符拒用 | 懒建集合时校验结构兼容性 |
| 失败语义 | 降级无注入，不阻断对话 | 混合策略降级单路；双写失败标 FAILED |

## 四个差异点的深读

**1. 父子分段是 solon-ai-example 的核心优势。** 子块检索准、父块上下文全，把「检索精度」和「上下文完整性」这对矛盾拆到两层去解。Ru41 靠「路径+标题拼进 embedding 文本」和重叠切块来弥补单粒度的局限，个人笔记场景够用，但面对长文档（比如几小时的课堂转写笔记），父子分段的上限明显更高。

**2. 同一个 RRF，融合哲学不同。** 加权 RRF 多了一组可调参（0.6/0.4），但注意权重乘在**未归一化**的 RRF 分上，真正起作用的是权重比；调不出收益时，无权 RRF 是更稳的默认。Ru41 干脆不加权——个人知识库里两路证据价值接近，少两个魔法数字。两边独立选中 k=60，说明这个「业界惯用值」确实经受住了不同场景的检验。

**3. 消费模型决定门控设计。** solon-ai-example 是「用户主动问」的搜索服务，天然不会拿寒暄当查询，所以不需要查询门控；Ru41 是「agent 自动注入」，短查询会白烧 token 还带偏回答，必须有长度下限。做 agent 方向的话，**自动注入场景的门控是必修课**——这一课 solon-ai-example 里没有。

**4. 中文分词殊途同归。** SQLite trigram 和 MySQL ngram 本质是同一个思路：用 N-gram 切词元，避开对中文分词器的依赖。副作用也一样——精确词（书名、错误码）是 dense 检索盲区，而 Ru41 的 FTS_HIT_FLOOR 抬分技巧在 MySQL ngram 上同样适用。

顺带一提，可靠性投入点跟部署形态严格对应：solon-ai-example 的重试、背压、懒连接都是为「网络 + 外部存储」买的保险；Ru41 全本地，一个 Mutex 就解决了并发，把精力花在脱敏链路上。架构复杂度应该花在真实的风险点上，两边都践行了这句话。

## solon-ai-example 的 RAG 后续探索方向

对比看完，主人这个项目下一步往哪走？本喵按「收益大、动手小」排了个序：

**1. 补上 agent 场景的查询门控（最推荐）。** 现在检索只由 REST 接口触发，一旦想接进 agent 做自动注入，第一个撞上的就是噪声查询。照抄 Ru41 的三个门控即可：查询长度下限（寒暄跳过）、上限（机器生成的长 prompt 跳过）、检索失败降级为无注入。改动集中在检索入口一处，半天工作量。

**2. 词面精确命中的分数抬升。** mysql-fulltext 路的相关度分和向量路的相似度分不同量纲，加权 RRF 之后原始分值已经失去可比性。可以学 Ru41：词面命中的文档，最终展示分抬到语义化下限之上，让「书名/错误码精确命中」不被向量路的语义泛化淹没。落地就是融合阶段几行代码。

**3. 检索结果的敏感信息处理。** 企业客服场景，知识库内容（FAQ、工单、内部文档）直接进 prompt 有泄露风险——尤其知识库是由多人维护的。在 `renderKnowledge` 之前加一道脱敏/过滤（正则规则表足够起步：手机号、密钥格式、内部域名），比事后依赖模型「不要输出敏感内容」的指令可靠得多。

**4. 两阶段重排（rerank）。** 父子分段天然适合：子块召回后先粗排，再加一层 cross-encoder rerank（bge-reranker 或 LLM 打分）筛出 top-k 的父块。RAG 本身已经用了远程 embedding 服务，加一个 rerank 服务的运维成本是边际的，而它对「召回对但排序乱」的场景提升最明显。做之前先建一个 20～50 条的 golden set（问题 → 应命中的文档 id），否则 rerank 的收益没法度量。

**5. 双写一致性的补偿机制。** 现在已知取舍是「MySQL↔Milvus 双写无原子性，失败标 FAILED」。最小代价的改进不是上分布式事务，而是加一个定时补偿任务：扫 FAILED 状态的文档重放入库流水线（`rebuildIndex` 已经具备幂等重放能力，就差一个触发器）。如果后续做多实例，再考虑 outbox 模式。

**6. 查询自适应路由。** 三种策略靠配置静态选择，但查询特征是动态的：含书名号、错误码、引号精确短语的查询走词面路更好，自然语言描述走向量路更好。可以在 Resolver 前加一层轻量路由（规则起步：检测精确词模式；不够再上小模型分类），把三种策略从「三选一」变成「按查询分发」。

1、2、3 是拿 Ru41 已验证的经验反向补强，属于「低风险抄作业」；4、5、6 是往生产化走的下一步，建议按 4（带评测集）→ 5 → 6 的顺序来，每步都有可度量的验收标准。

## 收尾

两套代码摆在一起看，最有意思的不是谁做得好，而是**规模决定形态**：Ru41 面对一个用户的 vault，把一切都压进一个 SQLite 文件，省下的运维预算花在检索卫生（门控、脱敏）上；solon-ai-example 面向多用户服务化，把钱花在分层（父子分段）、可插拔（策略模式）和可靠性（重试、背压、状态机）上。做技术选型时先问自己服务多少人、数据多大，答案自然就出来了。
